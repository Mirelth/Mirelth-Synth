## 一、结论

- **代码已全部完成并合入 `main`**：v7.6、v7.7、v7.8 三批工作都有对应提交。
- **没有发布**：没有 `v7.6.0` / `v7.7.0` / `v7.8.0` tag，也没有 `v7.5.2` tag。
- **版本号仍是 7.5.1**：`VERSION`、`pkg/agent.go`、TS SDK、Helm `appVersion` 全部一致为 7.5.1。
- **用户拿不到这些内容**：`go install ...@latest`、`ap version` 仍解析到 `v7.5.1`。
- 因此 CHANGELOG 里的 `v7.6` / `v7.7` / `v7.8` 是**工作批次代号**，不是已发布版本。

## 二、批次标记（非发布 tag）

为便于历史定位，仓库打了三个 **annotated tag**。它们不是 semver，不会进入 Go module proxy，也不会影响 `@latest`：

| Tag | 指向提交 | 定位 | 说明 |
|-----|----------|------|------|
| `batch/v7.6` | `2f9ab24d` | v7.6 最后一条修复（模板普查） | 已包含后续批次的部分代码（见 §三） |
| `batch/v7.7` | `73545a3e` | v7.7 副线（WASM 供应链 demo）完成 | 已包含提前落地的 v7.8 代码 |
| `batch/v7.8` | `fe23d75b` | 三批 CHANGELOG 收口、硬化批次之前 | 累计包含 7.6–7.8 全部内容 |

查看方式：

```bash
git show batch/v7.6
git log --oneline v7.5.1..batch/v7.7
```

## 三、为什么不能回溯成三个正式 semver tag

1. **提交交错**：v7.6 的最后两条修复（`84e70a90`、`2f9ab24d`）排在 v7.7（`b3ccd204`）和 v7.8（`27e59ec4`）之后。任何标成 `v7.6.0` 的提交都已包含 7.7/7.8 的代码；标早了又会漏掉 7.6 自己的修复。
2. **版本号未 bump**：候选提交（`21d58aee`、`2f9ab24d`、`73545a3e`、`9831cef3`）的 `VERSION` 全部是 7.5.1。打正式 `v7.8.0` 会让 Go proxy 把 `@latest` 指过去，用户装到自报 7.5.1 的代码。
3. **项目纪律**：版本路线 §八 明确写着 tag 与发布需维护者凭据、版本 bump 建议在发布时机确定后统一做；v7.6 的人类退出判据（非维护者按英文 README 15 分钟首胜）尚未记录。
4. **8.0 前置未签**：`deliverables/gstack/8.0-范围决定稿-2026-10-12.md` 尚待维护者逐项签署，v7.8 的“8.0 彩排”不能当作 8.0 已就绪。

逐项 commit 索引见版本路线 §八；面向用户的变更摘要见 [`docs/CHANGELOG.md`](CHANGELOG.md) 的 `[Unreleased]`。

## 五、正式发布前还缺什么

1. 统一版本 bump（Go `const Version`、`VERSION`、TS/Python/Rust SDK、Helm、文档锚点），并跑 `scripts/version-check.sh`、`scripts/version-sync-check.mjs`、`scripts/doc-version-consistency.mjs`。
2. 记录 v7.6 的人类退出判据（非维护者 15 分钟首胜）。
3. 维护者签署 8.0 范围决定稿；未签署前不执行任何删除。
4. 补发布说明与发布资产（npm / cosign / SBOM 等遗留项）。
5. 决定发布形态：由于三批代码已交错，建议一次发布为一个版本（例如 7.6.0），而不是回溯拆成三个版本。
